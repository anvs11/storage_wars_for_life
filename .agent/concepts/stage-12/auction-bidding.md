# Stage 12 – Система торгов (Auction Bidding Audit)

**Цель:** спроектировать честную и понятную механику аукциона, заменяющую текущую «по кругу» схему предложений. В открытом английском (open-outcry, ascending-price) аукционе ведущий объявляет цену, и **любой** участник может перебить её повышенной ставкой. Нынешняя логика (игрок пропускает ходы) этому не соответствует. Ниже приведён анализ, рекомендации и техническое ТЗ.

## Текущая реализация и проблема

В реальной игре **Storage Wars for Life** стадия торгов реализована через механизмы `stage7-engine` и связанные UI/логика. Согласно описанию владельца, сейчас после объявления цены право поставить ставок распределяется по очереди между NPC и игроком, из-за чего игрок часто пропускает раунд. Это похоже на **круговой аукцион** (circle auction) или фиксированный ход по правилам, что нежелательно.

- **Проблема:** игрок не может участвовать в каждом новом шаге, хотя хотел бы; NPC перегибают ставки последовательно, создавая «каждый по очереди» аукцион.  
- **Ожидаемая модель:** по аналогии с телевизионными шоу и играми типа Bid Wars, все участники должны иметь возможность увеличивать ставку на каждом шаге, без принудительного пропуска.

Нужно переработать аукцион в **открытый повышающийся аукцион** (open ascending auction). При объявлении ведущим новой цены каждый участник (кроме текущего лидера) должен иметь кнопку «согласен» (или «повысить до X»). Первый, кто нажмёт, становится лидером на этом уровне цены, и аукцион переходит к следующему шагу с новой ценой. Если никто не перебил текущее предложение за отведённое время, выигрывает текущий лидер.

## Открытый повышающийся аукцион

**Правила открытого аукциона:** 
- Аукционист объявляет стартовую (или новую) цену. 
- Все участники могут за неё бороться (повысить ставку) одновременно. 
- Тот, кто первый принимает цену, становится «ведущим» (standing bidder) на данном уровне. 
- Ведущий удерживает право выкупа до тех пор, пока другой игрок не предложит больше. 
- После перехода к следующей цене участвовать могут все, кроме текущего лидера. Если лидер перебит, он автоматически может делать ставки вновь при следующих повышениях. 
- Если за определённый тайм-аут никто не перебивает, аукцион завершается – предмет продаётся лидеру по его ставке. 

Таким образом, модель соответствует реальному **английскому аукциону**. Интерфейс должен подчеркнуть эти правила:
- Кнопка **«Повысить ставку до X»** активна, когда объявлена новая цена **X** (для игрока, если у него достаточно средств). 
- Виджеты участников (иконки/аватары) подсвечивают текущего лидера, показывая, кто предложил последнюю ставку.
- Фразы ведущего: «Следующая цена – ___» и предупреждения «торги завершены» и т.д. – прозрачно отображаются.

## Модель состояний аукциона (State Machine)

Предлагаемая модель состояний аукциона:  

```mermaid
flowchart TD
  start(Начало аукциона) --> announce{Объявление цены}
  announce --> bidding[Ставки участников]
  bidding --> check{Новый лидер?}
  check -->|да| announceNext{Переход к следующей цене}
  check -->|нет| finalize[Финальный отсчёт]
  announceNext --> bidding
  finalize --> end(Конец аукциона)
```

- **Объявление цены:** ведущий переходит к новой цене (увеличивает текущую цену на заданный шаг). Устанавливаются метки времени и очередь для ставок.
- **Ставки участников:** всем игрокам (игроку и NPC), кроме предыдущего лидера, разрешается нажать «согласен». Событие первой ставки фиксирует нового лидера.  
- **Переход к следующей цене:** как только ставка принята, возвращаемся к этапу «Объявление цены» с обновлённым лидером и ценой. Предыдущий лидер теперь может участвовать в новых шагах.  
- **Финальный отсчёт:** если таймер ставки истёк и ставки больше не поступают, проводится таймер (say "торг идёт последние раз") и, если ставки не растут, аукцион закрывается. 
- **Конец аукциона:** предмет продаётся лидеру, списываются средства, выдаются лот и очки репутации.

**Состояния и события:**
- **Pending (Ожидание повышения):** ведущий готовит следующую цену.  
- **Bidding (Ставка):** выполняется окно для ставок. Если игрок и/или NPC нажали «согласен», фиксируется победитель раунда.  
- **Final Countdown:** двойной таймер «последний шаг» («торг идёт…»).  
- **Closed (Закрыто):** аукцион завершён.  

**Инварианты:**
- Лидер в каждый момент – единственный текущий победитель ставки.  
- Цены всегда возрастают (не меняются в пределах одной ставки).  
- Количество участников постоянное, исключения – персонализированные паузы или выходы (withdraw).  
- Никогда не меняем экономические параметры (встроенная логика расчёта цен, бонусов и т.д.).  

## Логика ставок и обработки событий

Ниже — псевдокод основных функций аукциона. Это поможет Codex правильно реализовать логику без рефакторинга несвязанного кода:

```ts
interface AuctionState {
  currentPrice: number;
  leader: string | null;      // e.g. "player", "npc1", "npc2"
  askVersion: number;         // версия шага для отмены старых ставок
  stage: "Pending" | "Bidding" | "Final" | "Closed";
  bids: Record<string, number>; // последние принятые ставки участников
}

function announceNextPrice(state: AuctionState): AuctionState {
  // Увеличиваем currentPrice, обновляем версию шага
  state.currentPrice += calculateIncrement(state.currentPrice);
  state.askVersion += 1;
  state.stage = "Bidding";
  startBidTimer(state.askVersion);
  return state;
}

function placeBid(state: AuctionState, participant: string, version: number): AuctionState {
  // Игнорируем ставки для устаревших объявлений
  if (version !== state.askVersion || state.stage !== "Bidding") return state;
  // Если участник не предыдущий лидер и имеет деньги
  if (participant !== state.leader && canAfford(participant, state.currentPrice)) {
    state.leader = participant;
    state.bids[participant] = state.currentPrice;
    // немедленный переход к следующей цене (обновление ставки)
    clearTimers();
    return announceNextPrice(state);
  }
  return state;
}

function onBidTimeout(state: AuctionState): AuctionState {
  if (state.stage !== "Bidding") return state;
  // Если лидер есть, переходим к финальному отсчёту
  if (state.leader) {
    state.stage = "Final";
    startFinalCountdown(state.askVersion);
  } else {
    // Никто не участвовал (редкий случай) – можно попытаться повторить или закрыть аукцион
    state.stage = "Closed";
  }
  return state;
}

function finalizeAuction(state: AuctionState): AuctionState {
  // Завершение аукциона: выдаём выигрыш лидеру
  awardItemTo(state.leader, state.currentPrice);
  state.stage = "Closed";
  return state;
}
```

**Порядок событий (пример):** при старте аукциона `state.leader = null`. Ведущий называет цену (например, **100**), все могут ставить. Игрок нажал «Согласен» первым – `state.leader = "player"`. Обновляем цену, например, до **150**. Теперь участвуют все, **кроме** игрока: NPC1 и NPC2. NPC2 перебивает до **150** → `state.leader = "npc2"`. Следующая цена **200**: участвуют игрок и NPC1; игрок нажимает – `state.leader = "player"`, и т.д. Если в какой-то раунд больше никто не нажал — запущен финальный отсчёт, предмет уходит лидеру.

**Кнопки и события:**  
- «Повысить до X»: доступна игроку, если `participant == "player"`, у игрока ≥X рублей, и `stage == "Bidding"`, `player != leader`.  
- Если игрок нажал, зовётся `placeBid(player)`. Дальнейшие события блокируются (отмена старого таймера, сразу ставим новую цену).  
- NPC действуют аналогично через AI (см. ниже).  

**UI-фидбэк:**  
- Подсветка текущего лидера (аватар с рамкой/эффектом).  
- Показ текущей цены и следующей возможной.  
- Кнопка «Пас» (withdraw) = отказаться от аукциона окончательно, кнопка «Пропустить» = пропустить этот раунд (конкретная реализация не требуется, главное – игрок может не участвовать, но это не означает уход).  

## Поведение NPC (AI)

NPC должны действовать честно, без знания скрытых характеристик лота или «подстройки» под игрока. Предлагаемый подход:

1. **Бюджет и ценность:** каждому NPC задаются общие *ценность лота* и *бюджет*. Ценность можно вывести из категории лота (уже известной после вскрытия) с небольшим разбросом. Бюджет – константа для одного аукциона или кампании (например, 500–1000 ₽) с вариацией по персонажу.  
2. **Оценка ставки:** NPC рассматривает текущую цену и максимально доступную для него цену. Если `currentPrice` меньше его собственной оценки ценности, он может участвовать. Обычно NPC хочет выиграть лот, если `currentPrice < value`, но прекращает, когда цена достигает его предела.  
3. **Шанс и тайминги:** при объявлении цены даём каждому NPC небольшую задержку (сто мс – секунда) перед решением – имитируем мышление. Если игрок первым перехватывает, другие отменяют действие. Если NPC первый, они “нажимают” и становятся лидером. Задержки и рандомизация поощряют вариативность (один NPC может сразу отреагировать, другой – «проспит» и уступит).  
4. **Pass vs Withdraw:** NPC никогда не полностью «выбывает» из аукциона по пасу (кроме если превысил бюджет). Если NPC пропустил раунд, он может вернуться при следующем увеличении цены. Withdraw (снятие лота) у NPC обычно означает, что цена стала выше его бюджета – он больше не участвует.  

Важные моменты для ИИ: 

- **Определённость:** использовать **seeded RNG** для псевдослучайности действий NPC (чтобы поведение было детерминированным и воспроизводимым).  
- **Индивидуальность:** разным NPC – разные «характеры» (агрессивный, осторожный), которые меняют их willingness-to-pay множителем (например, 90–110% от базовой ценности).  
- **Правила приёма ставок:** NPC делают ставки без кооперации; не должны скрытно повышать ставку, если видят, что игрок можно перебить (честное состязание). Их цель – максимизировать свою выгоду и шанс выигрыша.  
- **Взаимодействие с таймерами:** если NPC решил действовать, но игрок в этот момент выиграл, сбрасывать их попытку (рейсы обрабатываются по версии `askVersion`).  

## Интерфейс аукциона

Интерфейс должен соответствовать «игровой реальности»: 

- **Ведущий и слоганы:** отображать текст ведущего и/или таймер («Поторгуемся за 100 ₽», «100 ₽, кто даст 150?», «Торг окончен»).  
- **Участники:** список из трёх-четырёх участников: игрок и NPC. У лидера – подчеркнутая рамка; на остальных – обычный вид. Под картинкой каждого – текущая его ставка.  
- **Кнопки:** «Повысить до X ₽» (где X = nextPrice) и «Пас». Кнопка «Повысить» неактивна, если у игрока нет денег или он уже лидер. Кнопка «Пас» (если вводится) однократно покидает аукцион.  
- **Анимация:** при нажатии на «Повысить» или при хождении NPC – короткий эффект (мигание рамки, звук), чтобы подчеркнуть событие. При окончании аукциона – переход на экран итогов и выигранный лот.  

Пример макета (desktop/mobile):

```
+-------------------------------+
| Торги за 50 ₽ (Банк: 1200 ₽)  |   <-- HUD
+-------------------------------+
| [Игрок]  [NPC1]  [NPC2]       |   <-- Аватары, лидера подсвечено
|  0 ₽      0 ₽     0 ₽         |
+-------------------------------+
| Предмет: Велосипед            |   <-- Изображение лота
|                               |
| Ведущий: "100 ₽, кто даст 150?"|   <-- Сообщение ведущего
+-------------------------------+
| [Повысить до 150 ₽]  [Пас]    |
+-------------------------------+
```

Все элементы интерфейса должны адаптироваться под мобильные разрешения без горизонтального скролла. Кнопки — размер ≥44×44 CSS px. Поддержать навигацию с клавиатуры и учесть `prefers-reduced-motion`. 

## Тестирование и приёмка

**Критерии готовности:** 

- Аукцион действительно работает как открытый, все игроки имеют равные права сделать ставку при каждой цене.  
- После объявления ставки, если лидер не изменился и таймер истёк, лот продаётся текущему лидеру.  
- При отстутствии ставок аукцион завершает работу (не застревает).  
- Игрок может всегда нажать «Повысить», если у него деньги и он не текущий лидер.  
- Отладочные скриншоты до/после должны демонстрировать новый UI (активные/неактивные кнопки, подсветку).  

**Тесты:** 
- *Unit tests:* логику `announceNextPrice`, `placeBid`, `onBidTimeout`, `finalizeAuction` – проверка переходов состояний при разных последовательностях событий.  
- *Интеграционные:* симуляция полного аукциона с заданными сценариями (например, фиксированный набор NPC-решений) – убедиться, что лот забирает ожидаемый победитель.  
- *E2E:* на «боевом» codebase имитировать несколько аукционов подряд, убеждаясь в отсутствии зависаний и корректном начислении средств/предметов. Использовать **fake timers** для таймаутов, **seeded RNG** для ИИ и проверить логи (например, currentLeader корректно меняется).  
- *Регрессии:* проверить сохранения (stage7-save), убедиться, что сохранение/загрузка точно восстанавливают состояние незавершённого аукциона, а после завершения – соответствующие изменения (денег, предметов, отзыв).  

**Метрики:** частота выигрыша игрока vs NPC (должна быть разумной, например ~1/3 при равных условиях), среднее количество поднятий ставки, время на аукцион (не слишком затягивается). 

## Рекомендации и план реализации

**Приоритет (P0):**  
- Перевести логику на открытую схему ставок как описано выше.  
- Убрать «круговую» очередность: разрешать ставку сразу всем (через события).  
- Реализовать state machine, обеспечить атомарность событий (askVersion, таймеры).  
- Подключить базовую NPC-логику (решение по цене и таймаут).  
- Обновить UI: «Повысить ставку» и подсветка лидера.  
- Проверить, что основная экономика (списание средств, получение лота, репутация) не изменилась.  

**Дополнения (P1):**  
- Уточнить политику «Пас»: сделать кнопку «Пропустить» вместо «Выбыть», чтобы игрок мог вернуться в следующий раунд.  
- Улучшить анимации ставок, тексты ведущего (например, «Новый шаг: ___ ₽»).  
- Расширенные профили NPC (стратегии, бюджеты, задержки).  

**Не делать:**  
- Не менять правила начисления денег/цен; не добавлять комиссии или двойное списание.  
- Не трогать unrelated модули (торги должны интегрироваться с текущим `stage7-engine` и не ломать `stage5` и `stage8`).  
- Не вводить обязательных внешних сервисов или ИИ.
