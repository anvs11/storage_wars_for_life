Документ создан физически в этой сессии и содержит полный анализ, предлагаемую архитектуру, схему данных, псевдокод, тестовую матрицу, критерии приёмки и готовый промпт для Codex. Ниже приведена его основная содержательная часть, чтобы результат не зависел от скачивания файла.

## Главный вывод

Ситуация с тремя одинаковыми тисками — не единичная неудача RNG. В текущем генераторе обычный `workshop`-лот имеет **три видимых слота, каждый из которых независимо выбирается из одного и того же пула** `drill / vise / level / wrench`. Для ordinary tier веса редкости составляют `75 / 22 / 3`, а после выбора редкости предмет выбирается из соответствующего подмножества без исключения уже выбранных `catalogId`. Поэтому выбор фактически происходит **с возвращением**, и никаких ограничений на повторы внутри лота сейчас нет. citeturn943969view0turn943969view1

В workshop-пуле common-предметов только два — дрель и тиски. Поэтому для отдельного видимого слота вероятность тисков равна `0,75 × 0,5 = 0,375`. Отсюда теоретическая вероятность получить три тиска подряд внутри workshop-шаблона составляет `0,375³ ≈ 5,27%`, а вероятность получить хотя бы два тиска — около `31,64%`. Это расчёт непосредственно из текущих весов и состава пула, а не результат симуляции. citeturn943969view0turn943969view1

Есть и более широкая проблема: на каждый tier сейчас предусмотрено всего **два шаблона**. Ordinary использует workshop или household, selected — две комбинации audio/equipment, antique — две комбинации ceramic/heirlooms. Поэтому даже после запрета точных дубликатов игрок сравнительно быстро начнёт видеть похожие композиции. citeturn943969view0

Сам seeded RNG менять не нужно. `stage3-engine.ts` уже передаёт генератору seed конкретного лота, а `repeat-auctions.ts` создаёт повторяемый `seededRandom`; отдельно seeded stream используется для лимитов соперников. Это хорошая архитектурная база для детерминированной генерации. citeturn316456view1turn943969view1turn943969view8

## Что происходит с ширмой и коробками

На присланном скриншоте справа действительно выглядит так, будто ширма и коробки являются одним объектом. Код подтверждает **визуальное объединение**: если предмет называется `Вещи за ширмой`, renderer создаёт sprite ширмы и затем в **тот же target DOM-элемент** добавляет `stackedBoxes()`. Поэтому исчезновение самого интерактивного target автоматически убирает и ширму, и декоративные коробки, находящиеся внутри него. citeturn943969view2

Это позволяет подтвердить архитектурную причину визуального поведения, но я бы пока не называл это доказанным багом логики инвентаря. Нужно отдельно проверить, при каком именно действии исчезает target: inspection, reveal, открытие контейнера или переход фазы. Система инвентаря уже оперирует конкретными `id` коробок и открывает содержимое по идентификатору, поэтому ошибка может быть ограничена presentation-слоем. citeturn943969view6

Правильная модель должна разделить три понятия:

```ts
type LotEntityKind =
  | "find"       // продаваемая вещь
  | "container"  // коробка, сундук, ящик с содержимым
  | "decor";     // ширма, палета, покрывало, полка
```

Ширма должна стать самостоятельным `decor/occluder`, а коробки за ней — отдельными `container` с собственными `instanceId`. Тогда открытие `box-01` не сможет удалить `screen-01` или `box-02`.

Например:

```json
[
  {
    "instanceId": "lot-12-decor-screen-1",
    "kind": "decor",
    "spriteId": "folding-screen",
    "decorRole": "occluder"
  },
  {
    "instanceId": "lot-12-box-1",
    "kind": "container",
    "contents": ["lot-12-box-1-item-1"]
  },
  {
    "instanceId": "lot-12-box-2",
    "kind": "container",
    "contents": ["lot-12-box-2-item-1"]
  }
]
```

При этом база для правильной идентичности уже существует: `fill()` создаёт уникальные ID вида `lot-N-visible-M`, `lot-N-box-M` и `lot-N-box-M-item-K`. То есть Codex не нужно заново придумывать систему экземпляров — нужно последовательно провести `instanceId` через renderer, reveal и interaction вместо опоры на имя или порядковый индекс. citeturn943969view1

## Что можно перенять из App Store-конкурентов

Точную игру с присланного ранее скриншота я не считаю надёжно идентифицированной. По композиции она очень близка к семейству **Bid Wars**: открытый storage unit, портреты участников слева, ведущий с репликой и набор визуально разных предметов внутри помещения. В App Store действительно существуют `Bid Wars 2: Pawn Shop Empire` и `Bid Wars: Storage Auctions`. citeturn316456view6turn316456view7

При этом нельзя утверждать, что нам известен их закрытый алгоритм генерации. Из официального описания первой Bid Wars известно только, что игра строится вокруг осмотра storage unit перед ставкой и содержит более 200 находок, включая редкие и старые предметы. Более современный `Storage Auction Tycoon: Bid War` заявляет более 350 предметов в 22 категориях, пять уровней редкости и механику открытия содержимого «box by box». Это показывает, насколько большой запас контента используют современные игры жанра, но не раскрывает их selection algorithm. citeturn316456view7turn316456view8

Для нас полезно перенять **наблюдаемый принцип композиции**, а не копировать конкретную игру: хороший лот выглядит как маленькая осмысленная сцена. В нём сочетаются разные силуэты и масштабы, часть объектов стоит на полу, часть — на поверхности или стойке, контейнеры создают неопределённость, а естественные повторы оформлены как комплект, а не как три независимо сгенерированных одинаковых предмета. Это дизайнерский вывод из визуальных референсов, а не утверждение о внутреннем коде конкурентов. citeturn316456view7turn316456view8

Stage 6 добавляет дополнительные variant items, но они в основном подменяют существующие слоты, а не превращают каждый тематический pool в большой уникальный каталог. citeturn943969view0turn943969view4turn943969view5

## Целевая модель генерации

Я бы оставил существующие `tier`, rarity weights, value budget, bid factors и 28 попыток подобрать содержимое по целевой стоимости. Сейчас `generateLot()` уже генерирует `targetValue`, пытается подобрать набор в пределах бюджета и выбирает ближайший допустимый результат; это важная экономическая логика, которую не стоит переписывать в рамках визуальной задачи. citeturn943969view1

Поверх неё стоит добавить **semantic composition layer**.

Сначала выбирается тема лота:

```ts
type LotTheme =
  | "workshop"
  | "household"
  | "audio"
  | "equipment"
  | "ceramic"
  | "heirlooms"
  | "mixed";
```

Затем template определяет количество visible/container/hidden объектов, primary и secondary families и допустимый decor:

```ts
interface LotTemplate {
  id: string;
  tier: AuctionTier;
  theme: LotTheme;

  visibleCount: readonly [number, number];
  containerCount: readonly [number, number];
  hiddenCount: readonly [number, number];

  primaryFamilies: readonly string[];
  secondaryFamilies: readonly string[];
  allowedDecor: readonly string[];
}
```

Для каждого definition вводится политика повторов:

```ts
interface RepeatPolicy {
  maxVisiblePerLot: number;
  maxTotalPerLot: number;
  cooldownLots: number;
  groupable?: boolean;
}
```

Default:

```ts
{
  maxVisiblePerLot: 1,
  maxTotalPerLot: 1,
  cooldownLots: 2
}
```

После выбора item его `catalogId` исключается из обычного candidate pool. Повтор разрешён только если definition явно обозначен как естественный набор.

Например, не:

```text
Колонка
Колонка
```

а:

```ts
{
  catalogId: "speaker-pair",
  quantity: 2,
  visualVariant: "pair"
}
```

То же относится к набору стульев, колёсам, книгам, тарелкам, дискам и другим предметам, которые действительно логично встречаются несколькими одинаковыми экземплярами.

Нужно добавить и **soft anti-repeat между соседними лотами**. Полный запрет на повторение выглядел бы искусственно, поэтому лучше снижать score недавно показанных вещей:

```ts
if (seenInPreviousLot) {
  score *= 0.15;
} else if (seenInPreviousTwoLots) {
  score *= 0.45;
}
```

Можно хранить компактную подпись последних лотов:

```ts
interface LotSignature {
  theme: LotTheme;
  catalogIds: readonly string[];
  families: readonly string[];
}
```

Отдельно рекомендую разделить RNG streams:

```ts
themeRng
itemRng
hiddenRng
layoutRng
decorRng
opponentRng
```

Это важно: изменение визуальной раскладки или добавление палеты не должно неожиданно изменить ценность лота или решения NPC. В текущем коде уже используется отдельный seeded stream для opponent limits, а Stage 6 применяет derived randomness при модификации состава, поэтому такой подход естественно продолжает существующую архитектуру. citeturn943969view1turn943969view4

## Визуальная раскладка предметов

Сейчас аукционная сцена всё ещё во многом располагает предметы по порядковым классам и fixed-позициям, а `mount.ts` передаёт в `placeProp()` `findIndex` или `boxIndex`. Это означает, что система знает «первый предмет / второй предмет», но не знает, насколько физически широки тиски, велосипед или коробка. citeturn943969view2turn316456view5

Вместо этого у каждого item должна появиться визуальная метаинформация:

```ts
interface ItemVisualDefinition {
  spriteId: string;

  footprint: {
    width: number;
    depth: number;
    height: number;
  };

  anchor: {
    x: number;
    y: number;
  };

  allowedSurfaces:
    Array<"floor" | "bench" | "shelf" | "rack" | "wall">;

  scale: {
    min: number;
    max: number;
  };

  collisionPadding: number;

  contactShadow: {
    width: number;
    opacity: number;
    blur: number;
  };
}
```

А сама сцена получает surfaces:

```ts
interface SceneSurface {
  id: string;
  type: "floor" | "bench" | "shelf" | "rack";
  polygon: Array<[number, number]>;
  depthRange: [number, number];
  scaleRange: [number, number];
}
```

Placement должен быть детерминированным: сначала самые крупные footprint, затем меньшие; для предмета генерируются допустимые poses на подходящих surfaces; варианты с выходом за поверхность и сильными пересечениями отбрасываются; после размещения добавляется контактная тень, а z-index рассчитывается по нижней точке объекта. Если крупный объект физически не помещается, лучше выбрать другой candidate до финализации лота, чем положить две вещи друг на друга.

Очень желательно также перестать выбирать sprite по `displayName`. `sceneSprite()` сейчас сопоставляет изображения с предметами по регулярным выражениям имени, поэтому разные definitions могут визуально схлопываться в один archetype. Более устойчиво использовать прямую связь `catalogId → spriteId`, а имя оставить только для текста UI. citeturn943969view3

Эта система хорошо сочетается с уже утверждённым Stage 12: транспортоподобный объект может стоять внутри auction unit во время торгов, но после доставки переносится в наружную зону игрока и не расходует внутреннюю вместимость дома. Для собственного гаража уже существует отдельная slot/surface-подобная 2.5D-система, поэтому часть принципов можно переиспользовать, не смешивая auction placement и inventory capacity. fileciteturn0file0

## Проверка качества и критерии приёмки

Автоматическая проверка здесь особенно полезна: неприятные повторения могут не встретиться в пяти ручных лотах, но быстро проявятся на нескольких тысячах seed. Это предложение по QA; фактический массовый прогон в рамках исследования не выполнялся.

Для каждого tier я бы прогнал минимум 5 000 seed и собирал duplicate rate, unique-visible ratio, rarity distribution, value-budget deviation, theme share, fallback rate, collision rate и overflow rate. Для соседних лотов полезна Jaccard similarity по `catalogId`: она покажет случаи, когда три-четыре последовательных гаража почти одинаковы.

Ключевые acceptance criteria:

- один и тот же `seed + tier + lotNumber + relevant state` даёт идентичный logical lot;
- все `instanceId` внутри лота уникальны;
- один `catalogId` не появляется дважды среди visible items без explicit `repeatPolicy`;
- естественные наборы представлены grouped entity;
- открытие одного container не изменяет другой container;
- ширма является отдельным decor и не исчезает при открытии коробки;
- клики и removal идут по `instanceId`, а не по `displayName`;
- value budgets и rarity weights сохраняют текущую экономическую модель;
- изменение layout не меняет состав и стоимость лота;
- существующие правила ставок, NPC, ремонта, отзывов и перевозки не меняются;
- старые сохранения продолжают загружаться;
- mobile-проверки выполняются хотя бы на `360×640`, `390×844`, `768×1024`, desktop — `1366×768` и `1920×1080`.

Публичная страница репозитория сейчас показывает ветку `main` и историю проекта, но доступное веб-представление не даёт мне надёжно зафиксировать фактический текущий SHA HEAD. Поэтому Codex должен первым шагом выполнить `git rev-parse HEAD` в своей рабочей копии, а не использовать SHA из старого исследования как источник истины. citeturn316456view0

Готовый промпт уже включён в скачиваемый Markdown. Его ключевая установка: **сначала аудит актуального HEAD, `npm test` и `npm run build`, затем карта изменений; реализация — без скрытого изменения экономики и без CSS-костылей вместо исправления модели данных**.
