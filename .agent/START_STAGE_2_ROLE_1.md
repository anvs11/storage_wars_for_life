# Stage 2 · У1 · Правила, сохранения и подключение

Основа — `ed702bb` из `origin/main` с закрытым Stage 1. Цель на дни 3–4 описана в .agent/EXECPLAN.md. Игрок проходит четыре кадра, начинает торги со $100, продаёт находки из двух разных гаражей и продолжает третий после обновления страницы. Владелец общего плана и точки входа `src/main.ts` — У1. У2 ведёт весь `src/ui/` и свой отчёт.

Каждая цитата ниже — отдельный промт. Для фиксации контракта и восстановления сохранений подойдёт GPT-6.2 Astra High, для реализации механик по согласованному контракту — GPT-6.2 Sol High. При работе на предыдущем поколении — GPT-6.1 Sol High.

## Порядок параллельной работы

Оба участника начинают от `ed702bb` или его согласованного потомка. Для отдельных копий используйте ветки `stage-2/role-1` и `stage-2/role-2`. Если агенты работают на одном компьютере, держите разные рабочие каталоги, чтобы переключение ветки не меняло файлы соседа. Сначала У1 передаёт один компилируемый коммит с типами и примерами. Он может идти отдельной веткой, но обе ветки реализации должны включать именно этот коммит. У2 до него готовит пролог и визуалы. После него оба ведут работу параллельно вплоть до тестового соединения веток. У1 владеет `src/game/`, `src/platform/`, `src/main.ts` и файлами сборки. Затрагивающее обе стороны изменение контракта фиксируйте одним согласованным коммитом, чтобы типы и примеры обновлялись вместе.

## Контракт, который передаём первым

Добавь `src/game/stage2-contract.ts`. Он использует типы Stage 1 из `src/game/contract.ts`, а прежние экспорты сохраняются на время параллельной реализации, чтобы экран и точка входа Stage 1 продолжали собираться. Новые публичные типы включают `Stage2View`, `Stage2Command`, `Stage2Dispatch` и `Stage2Mount`. При интеграции переведи основной движок и точку входа на них. Используй прежние `ItemId`, `VisibleItem`, `RevealedFind`, `SoldReceipt` и `PassedReceipt` там, где их смысл остался прежним. Состояние и правила остаются в одном движке.

- `Stage2Command` объединяет прежний `Command` и новые команды. Все новые команды содержат `expectedRevision: number`. В прологе используются `storyNext`, `skipStory`, `confirmRent`, в раскрытии — `openBox` с `boxId: ItemId` и `sellItem` с `itemId: ItemId`, при восстановлении — `sortGarage`. `Stage2Dispatch = (command: Stage2Command) => void`, `Stage2Mount = (root: HTMLElement, view: Stage2View, dispatch: Stage2Dispatch) => void`.
- `Stage2View` — объединение по `phase`. Общие поля для всех фаз — `revision: number`, `bank: number`, `allowedActions: readonly Stage2Command['type'][]`. Дополнительно экспортируй `Stage2AuctionView = Extract<Stage2View, { phase: 'inspection' | 'bidding' | 'reveal' | 'result' }>` для панели гаража.
- `prologue` содержит `story`. Это одно из `{ step: 'door' }`, `{ step: 'rain' }`, `{ step: 'dialogue'; line: 0 | 1 | 2 | 3 | 4 | 5 }` или `{ step: 'rent'; grant: number; rent: number; remaining: number; rentalWeeks: number }`. В начале `bank = 0`. После шестой реплики экран аренды показывает по данным представления $200, $100, $100 и две недели. `skipStory` доступна на всех кадрах. `storyNext` ведёт до шага аренды, на котором основной кнопкой становится `confirmRent`. Обе команды завершения переводят в один и тот же первый гараж с $100, применяя деньги и аренду единожды. Пролог, включая текущую реплику, сохраняется.
- Все четыре аукционные фазы передают `lotNumber: number`, `sceneId: 'tutorial' | 'workshop' | 'household'` и привычные поля осмотра и ставок. `sceneId` выбирает композицию, `visibleItems` поставляет имена и подсказки. В `bidding` добавь `leaderName: string` для имени текущего соперника и сохрани `leadingBidder: 'opponent'`. `currentPrice` — текущая цена, `lastPlayerBid` — последняя цена игрока, `nextBidAmount` — цена на кнопке. Нет отдельной фазы ожидания ответа.
- `reveal` передаёт `purchasePrice: number`, `revenue: number` (уже зачислена), `sealedBoxes: readonly { id: ItemId; name: string }[]` и `revealedFinds: readonly RevealedFind[]` (только открытые непроданные находки). Открытие коробки заменяет её находками без выплаты. До открытия коробка видна после покупки только как название и ID. `sellItem` разрешена для открытой находки. `sellAll` продаёт видимый остаток и доступна при отсутствии закрытых коробок и наличии хотя бы одной открытой находки. Последняя продажа при пустом остатке сразу даёт `result`; покупная цена, вся выручка и прибыль поступают в прежней `receipt`. Продажа с прибылью даёт в состоянии 2 очка статуса одной транзакцией. Публичную шкалу статуса отложить до Stage 3.
- `recovery` содержит `minimumBid: number` и `reward: number`. Показывается вместо осмотра следующего лота, когда при входе банк ниже его стартовой ставки и предыдущий инвентарь пуст. `sortGarage` начисляет ровно разницу до минимума один раз и ведёт к этому же лоту. Если игрок снова обеднеет после новых сделок, заказ может стать доступен снова. В ходе торгов при нехватке на повышение доступен пас.

В `src/game/stage2-exampleViews.ts` передай компилируемые примеры с `satisfies Stage2View`. Экспорты для У2 — `stage2Views` с ключами `door`, `rain`, `dialogue` (реплика 0), `rent`, `inspection`, `bidding`, `revealSealed`, `revealPartial`, `sold`, `passed`, `recovery`. Учебный сценарий сохраняет $20 → $25 → $30, банк $70, открытый велосипед $35 и закрытую коробку до отдельного действия. Для `revealPartial` покажи банк $105, выручку $35, открытый инструмент $10 и пустой список коробок. Итог — $115 и прибыль $15. Числа и ревизии задаются примерами и движком. UI только отображает и отправляет команды.

## 1. День 3, начало работы. Передать типы и примеры

> Прочитай .agent/EXECPLAN.md, .agent/PLANS.md и раздел контракта в .agent/START_STAGE_2_ROLE_1.md. Подготовь только src/game/stage2-contract.ts и src/game/stage2-exampleViews.ts. Сохрани сборку Stage 1. Проверь npm test и npm run build. Сделай отдельный локальный коммит с двумя файлами и передай У2 его идентификатор, имена экспортов и путь к примерам. Согласуй один источник коммита для обеих веток. В записи о передаче укажи, что примеры вручную задают сценарии и пока не доказывают работу движка.

## 2. День 3–4. Реализовать правила и сохранения параллельно с У2

До общей сборки держи переходную реализацию движка и её тесты в `src/game/stage2-engine.ts` и `src/game/stage2-engine.test.ts`. Текущий `src/main.ts` по-прежнему использует рабочую пару Stage 1, поэтому ветки обеих ролей собираются отдельно. Переноси и переиспользуй проверенные расчёты ставок и квитанции. В общей сборке переведи `src/main.ts` на новые экспорты и оставь ровно один используемый движок и один путь тестирования правил. У2 таким же образом держит старый экспорт `mount` до общей сборки, а новый экран экспортирует как `mountStage2`.

> Продолжай на зафиксированном контракте. Подготовь src/game/stage2-engine.ts и его тесты рядом, добавь src/game/catalog.ts и src/platform/save.ts. Сделай три композиции на 12 типах предметов и три состояния с разными видимыми признаками и диапазонами. Сохрани первый учебный гараж с контрольными ценами и открытием коробки отдельной командой. Дальше выдавай две другие композиции в воспроизводимой последовательности. При создании лота один раз определяй находки, состояние, цены, шаг и пределы одного или двух покупателей. Каждый активный покупатель пробует повышение на один шаг в фиксированном порядке после ставки игрока. Пропустивший свою очередь из-за предела выбывает из этого лота. Списывай только принятую победную ставку. Если игрок пасует, сохраняй его банк. Держи текущий лот, выбывших покупателей, уже открытые коробки, оплаченные и проданные позиции в состоянии. На новую игру веди в пролог, а переход к его концу и пропуск должны дать один первый гараж с $100. Однократно начисляй прибыльный статус и оплату сортировки. Обнови затронутые сценарии Stage 1 под новый пролог и вскрытие коробки, сохрани проверку старых денежных инвариантов. Добавь проверки отказов, убыточной цепочки до заказа, двух покупателей, проданной позиции после повторной загрузки и отсутствия цены закрытой находки в представлении. Подготовь для У2 обычный путь воспроизведения убыточной цепочки с названиями лотов, ставками и ожидаемым банком.

> Сохраняй версионированный снимок после каждой принятой команды. Проверь полный снимок при чтении, включая фазу и соответствующие ей поля. Держи предыдущую корректную копию, при её использовании выведи понятное сообщение. При отсутствии пригодных копий явно сообщи игроку о проблеме и предложи начать новую игру. При ошибке записи сохраняй подтверждённый экран и дай повторить действие. Тестируй несовместимую версию, повреждённый JSON, отказ записи и загрузку из каждой фазы. Сценарии с локальным хранилищем сначала проверь через тестовый объект. Работа UI идёт отдельно, поэтому для тестов движка используй публичные команды и типизированные примеры. До объединения веток не меняй src/ui/. Готовность передачи — тесты, сборка ветки и маршрут с контрольными суммами, пригодный для независимого прогона.

## 3. День 4. Подключить ветку У2 и провести совместную приёмку

У1 подключает `import { mountStage2 as mount } from './ui/mount';`. У2 после первого успешного прогона общего приложения удаляет свой временный просмотр и старую реализацию экрана. У1 затем убирает старый движок и устаревшие фикстуры, сохраняя тесты принятых денежных сценариев в обновлённом виде.

> Объедини согласованные изменения У1 и У2 в общей проверочной ветке. В src/main.ts загрузи сохранение, а при его отсутствии создай профиль с прологом. После принятой команды сначала запиши снимок и только после успешной записи покажи новое состояние. Для сообщения о восстановлении, повреждении или ошибке записи используй доступную область рядом с контейнером экрана. Убедись, что mount остаётся с тремя аргументами. После проверки основного маршрута передай У2 удаление временной страницы и старого экрана. Затем убери временное сосуществование движков по описанному выше порядку. Из корня выполни npm test, npm run build, запусти npm run dev -- --host 127.0.0.1 --port 5173 --strictPort. Пройди оба пути пролога, две разные сделки и начало третьей со страницы /. Проверь перезагрузку на кадре, во время торгов, после покупки перед вскрытием, во время частичной продажи, на квитанции и перед сортировкой. Передай У2 точную ревизию и маршрут для независимой проверки. После его отчёта внеси в Progress, Decision Log и Outcomes & Retrospective только фактически проверенное. Выход этапа — две разные сделки, сохранённый третий лот и доступное восстановление капитала при реальном сценарии убытка.
